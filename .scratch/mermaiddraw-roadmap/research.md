## Excalidraw: callbacks, identity, and scene replacement

**Documented API.** The [official integration docs](https://docs.excalidraw.com/docs/@excalidraw/excalidraw/integration) document embedding the React component. The [official imperative API docs](https://docs.excalidraw.com/docs/@excalidraw/excalidraw/api/props/excalidraw-api) document the `excalidrawAPI` callback, `updateScene`, `getSceneElements`, `getSceneElementsIncludingDeleted`, and `onChange` subscription. `initialData` is for initialization ([docs](https://github.com/excalidraw/excalidraw/blob/a2ec2889babf7d2295469c6d90ebe77fae57df84/dev-docs/docs/%40excalidraw/excalidraw/api/props/initialdata.mdx)). The `onChange` prop/API receives elements, app state, and files; the public callback signature has no “user edit vs. programmatic update” origin field ([pinned types](https://github.com/excalidraw/excalidraw/blob/a2ec2889babf7d2295469c6d90ebe77fae57df84/packages/excalidraw/types.ts)).

**Pinned source observations.**

- `updateScene({ elements })` passes the supplied array through index normalization and calls `scene.replaceAllElements`; supplying the complete newly parsed array is therefore the source-level path for replacing the scene, not an element-level patch ([`App.tsx`](https://github.com/excalidraw/excalidraw/blob/a2ec2889babf7d2295469c6d90ebe77fae57df84/packages/excalidraw/components/App.tsx)). It also accepts `captureUpdate` to control undo/history capture, so the adapter must choose that deliberately.
- `convertToExcalidrawElements` regenerates IDs by default; `{ regenerateIds: false }` avoids that behavior ([official skeleton docs](https://docs.excalidraw.com/docs/sdk/excalidraw/api/excalidraw-element-skeleton), [pinned implementation](https://github.com/excalidraw/excalidraw/blob/a2ec2889babf7d2295469c6d90ebe77fae57df84/packages/excalidraw/data/transform.ts)). Keep this option explicit when converter IDs are the Mermaid-to-scene join key. `updateScene` itself replaces with the IDs supplied by the caller.
- The API exposes both non-deleted elements and elements including deleted ones; source confirms these are separate getters. An adapter can detect removed IDs by comparing snapshots and inspect deletion tombstones when needed. `onChange` provides the element list for observing changes, but should not be assumed to be user-originated.
- Excalidraw element IDs and `groupIds` are available to the adapter. Tracking moves by stable ID and mapping user-created groups are adapter responsibilities; no Mermaid-specific mapping exists in Excalidraw.

**Gap / recommendation.** No editor fork is indicated. Use `onChange` plus element IDs/coordinates/group IDs, compare element sets for deletes, and submit a full scene with `updateScene`. Add an adapter-side origin guard or revision/fingerprint check to prevent feedback loops. Verify drag, delete, grouping, undo, and callbacks caused by `updateScene` in the required runtime spike; source/docs do not establish echo behavior or all identity edge cases.

## `mermaid-to-excalidraw`: IDs, groups, edges, and layout

**Documented API.** The [official converter API docs](https://docs.excalidraw.com/docs/@excalidraw/mermaid-to-excalidraw/api) describe `parseMermaidToExcalidraw(definition, config)` returning element skeletons (and optional files), and state that labels are bound to shapes and flowchart edges/state transitions to connected shapes. The documented config includes font size, elbow routing, and parser limits—not a source-ID mapping or coordinate-preservation API. Invalid input rejects rather than yielding a valid new diagram.

**Pinned source observations** ([converter commit `5692176`](https://github.com/excalidraw/mermaid-to-excalidraw/tree/569217629e0a8b754686d7596a57e5568f715494)):

- `parseMermaidToExcalidraw` parses a graph and returns skeletons; [Pele](https://github.com/excalidraw/mermaid-to-excalidraw/blob/569217629e0a8b754686d7596a57e5568f715494/src/parseDiagram.ts) does the Mermaid parse/layout. The [flowchart parser](https://github.com/excalidraw/mermaid-to-excalidraw/blob/569217629e0a8b754686d7596a57e5568f715494/src/pele/flowchart.ts) recovers node and subgraph IDs from Pele's model. The [converter](https://github.com/excalidraw/mermaid-to-excalidraw/blob/569217629e0a8b754686d7596a57e5568f715494/src/converter/types/flowchart.ts) assigns those IDs to node/subgraph skeletons and binds edge endpoints to the matching shape IDs.
- Edge IDs are generated as `` `${edge.start}_${edge.end}` `` rather than copied from the Mermaid edge ID. Thus endpoints can identify a simple edge, but parallel edges with the same endpoints can collide; that is a source-level risk, not a demonstrated runtime failure. The returned skeletons do not expose a source-edge-ID field.
- Subgraph rectangles carry their own IDs, but this converter initializes subgraph, regular-node, and edge `groupIds` as empty. It does not encode subgraph membership as Excalidraw grouping. A double-circle gets a converter-generated group for its component shapes; that is not Mermaid subgraph membership. The skeleton transformer supports IDs/group IDs ([source](https://github.com/excalidraw/mermaid-to-excalidraw/blob/569217629e0a8b754686d7596a57e5568f715494/src/converter/transformToExcalidrawSkeleton.ts)), but that does not make the missing source relationships available to callers.
- Baseline flowchart layout is Pele-generated. At this pin, defaults are font size 20, flowchart curve `linear`, node spacing `40 × 1.5 = 60`, rank spacing `48 × 1.5 = 72`, and `responsive: false` / `autoDirection: false`; a diagram's own config can override the flowchart config ([source](https://github.com/excalidraw/mermaid-to-excalidraw/blob/569217629e0a8b754686d7596a57e5568f715494/src/pele/parsePele.ts)). Pele's layout is read back from its rendered SVG before skeleton conversion. These are implementation defaults, not a stability promise across versions.

**Gap / recommendation.** Preserve node IDs by opting out of Excalidraw's default ID regeneration. An adapter can map ordinary nodes and subgraph shapes by those IDs, restore known coordinates after reparse, and track user-created Excalidraw groups. It cannot reliably recover parallel-edge identity or subgraph membership from the current returned skeletons alone. A robust solution for those needs is an upstream converter API that emits source edge IDs and parent/subgraph membership (or an adapter that independently parses/correlates Mermaid, which is not thin). Exact layout controls or stable layout across converter upgrades likewise need an upstream contract; coordinate metadata and ID-based post-processing are adapter candidates but need a spike, especially for routing and changed graph structure.

## Evidence limits and next proof

The hosted [playground](https://mermaid-to-excalidraw.vercel.app/) was not interacted with; its landing page is not evidence of a stable API. No package code was executed and no browser/runtime behavior was tested. In particular, test the exact npm tarballs for 3.6.0 and 0.18.1, converter ID retention with Excalidraw conversion, parallel edges, groups/subgraphs, `onChange` after `updateScene`, deletion, and position round-trips before deciding whether the converter needs an upstream change or fork.
